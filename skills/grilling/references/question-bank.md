# Grilling 提问清单

**用法：不要一次把清单倒给用户。** 一次只从一个分支里挑一个问题问，得到答案后决定下一步走向哪个分支。
下面是每个分支的备选问句，大致按"从抽象到具体"排列。

## 1. 目标

- 这东西存在是为了解决谁的什么问题？用一句话说。
- 如果它完全不出现，现在会发生什么坏事？
- "做完了"是什么样子？给我一个能观察到的事实。
- 三个月后回头看，什么情况会让你觉得"这个项目失败了"？
- 最重要的那一个指标是什么？其他都是次要的吗？

## 2. 范围

- 这次明确**不做**什么？
- 第一版最小可用是什么？砍到不能再砍是什么样？
- 有没有"顺手也做了吧"的东西？那些应该砍掉。
- 有没有依赖别人还没做的东西？

## 3. 用户与场景

- 谁用？一个人还是多个人？角色有区分吗？
- 多久用一次？一天十次还是一年一次？
- 用错了会怎样？会丢数据吗？会泄露吗？会花钱吗？
- 用户当时的注意力在哪？他会读提示文字吗？
- 新用户第一次打开，怎么知道该干什么？

## 4. 数据

- 什么数据进来？格式是什么？谁保证格式？
- 什么数据出去？给谁？
- 存在哪？存多久？谁能看见？谁能改？
- 数据量级是多少？今天多少，一年后多少？
- 有没有敏感字段？需要脱敏或加密吗？
- 备份怎么恢复？试过吗？

## 5. 失败模式

- 网络断了会怎样？重试吗？幂等吗？
- 两个请求同时改同一条记录会怎样？
- 数据量涨 100 倍会怎样？哪里先崩？
- 依赖的外部服务挂了会怎样？降级还是报错？
- 磁盘满了 / 内存不够 / 超时了，分别会怎样？
- 用户看到一个错误页，他该做什么？

## 6. 边界与接口

- 这个模块和其他部分的边界在哪？
- 契约是什么？函数签名 / HTTP 接口 / 消息格式，直接写出来。
- 谁负责校验输入？边界内还是边界外？
- 这个模块能不能独立测试？怎么测？
- 改了这个模块的一行代码，会不会让系统另一头崩掉？

## 7. 不可逆决策

这类问题问得最狠，因为它们以后改起来最贵。

- 哪个选择以后改起来很贵？（数据模型 / 公开 API / 持久化格式 / 认证方案）
- 有没有办法把它变得可逆？加一层适配？先双写？
- 如果现在赌错了，退出成本是多少？
- 有没有一个"先做小、以后再扩"的版本？

## 8. 验收

- 怎么测试？单元测试覆盖什么？谁来写？
- 手工验收的步骤是什么？给一个 checklist。
- 上线的判定标准是什么？谁签字？
- 出问题怎么回滚？回滚需要多久？

---

## 追问话术：把含糊逼到具体

| 用户的含糊回答 | 你的追问 |
|---|---|
| "差不多就行" | "差的那一点是什么？给我一个具体数字。" |
| "看情况" | "举一个最好的情况和一个最坏的情况，分别怎么走？" |
| "到时候再说" | "那我们现在先假设一个默认行为，你同意吗？" |
| "应该不会发生" | "假设它真的发生了，我们要做什么？" |
| "你决定" | "哪一个约束最不能妥协？我按那个来。" |
| "性能要快" | "快到什么程度？P99 多少毫秒？现在是多少？" |
| "用户会觉得好用" | "哪个具体动作会变快，或者变少？" |
| "跟之前那个差不多" | "哪里一样，哪里不一样？不一样的那部分为什么要变？" |
| "我先想想" | 好。停下来等他想。**不要自己填答案。** |
| （沉默或转移话题） | 记下来"这里没定"——这是最大的风险点，收尾时必须复述。 |

## 收尾模板

```
已达成的关键决策：
1. <决策> —— 因为 <理由>
2. <决策> —— 因为 <理由>

未决 / 存疑：
- <没答上来的问题>（最大的风险点）
```

超过 5 行就说明访谈还不够收敛，别急着收尾。
