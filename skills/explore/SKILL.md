# Explore：先别急着提案

Explore 介于 Grilling（快、无产物）和 Brainstorming（慢、强制产物）之间。
它**没有固定步骤**，强调灵活和适应。

**默认不产出任何工件**——不写 proposal、不写 spec、不写 design、不写 tasks。
方向明确之后，把上下文交给后续的设计或计划流程。

它假设：**思考过程本身就是价值，不一定非要有最终输出。**

## 怎么用

面对一团乱麻时，按这个顺序陪用户走：

1. **先读，别先说。** 读代码、读配置、读 README、读 git log。把"实际情况"和"用户以为的情况"对齐。
2. **问出真实问题。** 不是收集需求，是帮用户把脑子里的乱麻理顺。用户描述的是症状，你要找的是病灶。
3. **划范围。** 这次到底想解决什么？明确不碰什么？
4. **比较选项。** 列出 2–3 条路线，各自的代价和不可逆点。
5. **画 ASCII 图。** 结构、数据流、状态转换——纯文本画，直接贴进代码注释或文档。

## ASCII 图建议

结构：

```
[Client] ──HTTP──> [API] ──> [DB]
                     │
                     └──> [Queue] ──> [Worker]
```

状态转换：

```
draft ──submit──> review ──approve──> published
  ^                  │
  └─────reject───────┘
```

不用打开画图软件，不用拖拽对齐。对工程师来说这种极简可视化很实用。

## 什么时候转入下一步

当能一句话说清"**要解决的问题 + 选定方向 + 主要代价**"时，就停下探索。

- 要一份可追溯的设计文档 → 转 `brainstorming`
- 已有初步方案只想验证漏洞 → 转 `grilling`
- 直接开始实现 → 结束探索

## 反模式

- 一直探索不收敛 → 探索是手段不是目的，给自己设时间盒（15–30 分钟）
- 走完之后什么都没留下 → 至少在对话里复述一次选定的方向和理由
- 把探索当成"先随便聊聊" → 每次提问都要有目的
- 明明该产出了还在探索 → 那是拖延，不是探索
