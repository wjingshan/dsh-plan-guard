# ASCII 图套路

纯文本画图的价值：不用画图软件、不用拖拽对齐，直接贴进代码注释 / 文档 / PR 描述，而且能对照 diff 看出变化。

四条规则：

1. **对齐比好看重要**（不过等宽字体下对齐本身就好看）
2. **一张图只讲一件事** —— 图里超过 7 个方块就该拆
3. **给图一个标题**，说明它讲的是哪个视角
4. **避免交叉连线** —— 交叉了就重新摆放

## 状态机

```
draft ──submit──> review ──approve──> published
  ^                  │
  └─────reject───────┘
```

带终态和重试：

```
       ┌──────── cancel ────────┐
       │                        ▼
  [新建] ──> [处理中] ──> [完成]  [已取消]
                │
                └── error ──> [失败] ── retry ──> [处理中]
```

要点：

- 方框 = 状态，箭头 = 事件，箭头上的字 = 触发条件
- 每个状态都要能走出去（除了终态）
- 有没有"死状态"（进得去出不来）？那就是 bug

## 数据流

```
输入文件 ──解析──> 中间结构 ──校验──> 规范化 ──> 存储
                      │
                      └── 校验失败 ──> 错误报告 ──> 用户
```

标注每一步的**数据形态**而不只是动作，通常更有用：

```
raw CSV          ParsedRow[]        ValidRow[]        DB row
   │                 │                  │               │
   ├── parse ───────>│                  │               │
   │                 ├── validate ─────>│               │
   │                 │                  ├── persist ───>│
```

## 决策树（帮用户想清楚，不是代码结构）

```
用户要排序？
├─ 是 ──> 数据量 > 10 万？
│          ├─ 是 ──> 服务端排序 + 分页
│          └─ 否 ──> 客户端排序
└─ 否 ──> 默认按创建时间倒序
```

## 什么时候不该画图

- 只有两三个组件、一条直线 → 一句话说完，别画
- 图画完比文字还长 → 用文字
- 你自己都不确定结构 → 先读代码，别用图掩盖不确定性
