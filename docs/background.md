# 这个仓库是怎么来的

不是设计出来的，是**踩出来的**。这份文档记录每条决定背后的原因，以及我们**主动放弃**了什么 —— 后半部分和前半部分一样重要。

---

## 一、起点：两台视频，两个互补的半边

### 第一台：写代码之前

拆解三个「规划型」框架：

- **Grilling**（Matt Pocock）—— 像咄咄逼人的面试官，一次只问一个问题，沿设计树追问到具体
- **Brainstorming**（Obra / Superpowers）—— 像严格的项目经理，九步流程，强制产出设计文档
- **Explore**（OpenSpec）—— 像好奇的思维伙伴，先读代码、比较选项、画 ASCII 图，默认不产出工件

三种哲学：**质量保证 / 过程管理 / 认知支持**。共同前提是「如果你能回答所有关键问题，这个计划就可靠」。

看完的结论：**这三个东西本质是提示词工件，不是软件。** 所以搬过来不需要开发框架 —— 直接写成 skill 就行。这是 `skills/` 那一半。

### 第二台：写代码之后

一位芯片验证工程师转做 AI Agent 后的反思：他 90% 的时间不是在写 Agent，而是在**手动验证它有没有坏**。

- 理论依据：Jason Wei 的 **验证的不对称性** —— 有很多任务做出来难、验证容易。顺着得到 **verifier's rule**：任何可解且易于验证的任务终将被 AI 解决。
- 推论链：把「判断做得对不对」从靠肉眼改造成自动可重复的体系 → 难验证问题变成易验证问题 → 剩下交给 AI。
- 他的方案：**双层裁判** —— ① 确定性断言（工具是否触发、中间状态多少条记录）② LLM 裁判（上下文必须干净、做量化打分而非判对错）。

看完的结论完全不同：**这一半的落点是工程架构，加 skill 解决不了。** 得挂到 DSH 的原生拦截缝上。这是 `plugins/` 那一半。

## 二、为什么只做「第一层」

第二个视频有五步：改造架构 → 双层裁判回归测试 → 攒案例 → 每个功能配 flag → 闭环。

我们**只做了「确定性断言」这一层的一部分**，而且是缩到最小的版本：不做用例库、不做 scoreboard、不做 flag 对比、不做覆盖度。

原因是三座山，一座都没动：

| 坎 | 为什么难 |
|---|---|
| **非确定性** | 单元测试同样输入永远同样输出；Agent 不是。于是必然要回答「这次失败是我的改动弄坏了，还是它今天心情不好」。视频对这点只用一句「容忍程度要更高一点」带过 —— 因为它没有方法，只能靠重复跑取多数、或者把断言放宽到硬指标。 |
| **成本** | 每个用例是一次完整的真实 agent 运行，分钟级 + token 钱。不能用「每次存盘都跑一遍」那种单元测试的用法。这是运行策略问题，不是编码问题。 |
| **裁判的信噪比** | 一个判错的 LLM 裁判比没有裁判更糟 —— 它会制造噪音，然后你会开始忽略它的输出，整套体系退化成装饰品。 |

所以这个仓库做的是**性价比最高的那一刀**：不建体系，只把已经真实踩过的坑固化成断言。它不让你「知道这次改动没弄坏别的」，它只让你「不重复踩同一个坑」—— 而后者恰好是零成本、确定性的。

## 三、每条判据的来历

**没有一条是编的。** 这是这个仓库最重要的约束：如果一条判据不能指向一次真实事故，就不该存在 —— 因为它会变成噪音，而噪音等于没有。

### `SHELL_ERREXIT_TRAP`

一个打包脚本里写着：

```bash
set -euo pipefail
other="$(ls -1 *.zip 2>/dev/null | grep -v "^$KEEP$" | wc -l | tr -d ' ')"
```

`grep -v` 在没有匹配时返回 1；`pipefail` 让管道里任何一段的失败都算整条管道的失败；赋值语句的退出码就是命令替换的退出码；于是 `set -e` **就此终止整个脚本 —— 没有任何报错、没有栈、没有提示，只是 exit 1**。

排查花了很久。修法是末尾加 `|| true`。

这条判据的全部复杂度都来自「位置和 shell 选项会改变结论」：

| 写法 | `set -e` 下 | 为什么 |
|---|---|---|
| `x=$(grep a f)` | ❌ | `$()` 退出码**就是**赋值退出码 |
| `echo $(grep a f)` | ✅ | 命令替换失败**不影响**外层命令的退出码 |
| `if grep -q a f; then` | ✅ | 条件位置的失败本来就是预期 |
| `[ -n "$(grep a f)" ]` | ✅ | 作数的是 `[` 的退出码 |
| `for f in $(ls *.md)` | ✅ | 不参与退出码 |
| `x=$(ls \| grep v \| wc -l)` 无 `pipefail` | ✅ | 只有最后一段作数 |
| 同上 **有 `pipefail`** | ❌ | 任何一段都算 |
| `x=$(grep a f \|\| true)` | ✅ | 显式吞掉 |
| `x=$(grep a f) \| cat` | ✅ | 子 shell，杀不了整个脚本 |
| `cat f \| { x=$(grep a f); }` | ❌ | 复合命令返回非零，照样致命 |

**最后两行是我写测试时写错才发现的。** 我原本断言「管道里的赋值都不该报」，测试失败后才发现：`x=$(...) | cat` 跑在子 shell 确实不该报，但 `cat f | { x=$(...); }` 的整个复合命令返回非零，**照样致命**。两种写法长得像，语义相反。于是加了 `isPipelineStage` 把它们分开。

### `SHELL_GREP_UNQUOTED_PATH`

```bash
grep -rn "description" $D
```

`$D` 展开为空时，这个操作数**整个消失**，grep 就去搜了别的地方 —— 把整个 workspace 递归搜了一遍，淹掉了真正的输出。

教训记下来的是「`grep -r` 前必须先确认变量非空」，但更准确的说法是：**没加引号的变量在参数位置是个隐形的操作数消失器**。修法是 `"${D:?}"`，让它为空时直接报错退出。

### `PS1_NO_BOM`

PowerShell 5.1 会把**没有 BOM 的 UTF-8** 当 ANSI 解码。一份中文 `.ps1` 在 Windows 上跑，中文全变乱码。macOS/Linux 上写的时候完全看不出来。

修法是把 content 的第一个字符设成 `\uFEFF`。

### `dsh-skill-lint` 那七条

来自一个更早的坑：**DSH 遇到写错 frontmatter 的 skill 会静默丢弃整个 skill**。模型端分不清「这个 skill 不存在」和「这个 skill 写错了」—— 目录里看不到任何诊断，只有日志里一条 warning。

我们为此在打包脚本里手写过一遍守卫（用 awk 比对 name 和目录名）。后来意识到：**手写守卫的问题是「你得记得跑它」**。挂到缝上之后，每一次写入都自动过一遍，不用记得。

## 四、主动放弃的东西

比做出来的东西更值得说明：

| 放弃 | 理由 |
|---|---|
| **不做通用 eval / 回归框架** | 非确定性、成本、裁判信噪比三座山。规模不到就上，等于给三个 skill 建一套 CI，正是第二个视频结尾警告的「本末倒置」。 |
| **不做「自动修复」** | `post-execute` 的 `accept` 能替换工具结果，但**改不了磁盘**。声称「我帮你回滚了」但没回滚，比明说「文件已改坏」危险得多。所以我们只报告。 |
| **不做跨文件 lint** | 只查单文件内容。跨文件一致性需要全局视图，那会引入「什么算一致」的主观判断，而主观判断不该进断言层。 |
| **不做正文内容质量检查** | 只查「DSH 会不会静默丢弃它」这类**确定性**事实。文笔、结构、可读性交给模型读 —— 断言不越界假扮评审官。 |
| **不把两个插件合成一个** | 独立装卸、名字准确、不冒着弄坏已验证插件的风险。代价是缝接线重复了约 60 行，接受。 |

## 五、参考

- `dsh-design-audit` —— 「测量与判据分离」这套分层的来源。它的自述是：*测量错、判据错可以分别审计，互不掩盖*。同一个作者还写了「机器只做可测量的判断，审美交给模型看图」，这句话直接影响了我们「不做正文质量检查」的决定。
- DSH 原生的 `tools/pre-execute` / `tools/post-execute` 拦截缝 —— `PreToolDecision` 的 `deny` 和 `PostToolDecision` 的 `block{feedback}` 就是第二个视频里「确定性断言」的原生形态。
- 普林斯顿 SWE-Agent 论文的 **Agent-Computer Interface（ACI）** 概念 —— 「AI 是一类全新的用户，接口设计好坏影响甚至大过换更强的模型」。这是「为什么值得给 AI 专门设计拦截点」的依据。
